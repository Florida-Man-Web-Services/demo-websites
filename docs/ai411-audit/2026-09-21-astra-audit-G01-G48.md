===DESIGN===
1. Audit position and scope

This is a comprehensive coverage inventory and ranked backlog based on the supplied ground truth. It is not a completed repository inspection, penetration test, live-service certification, or legal review.

The supplied facts establish substantial existing functionality. They do not establish that every function has a usable interface, durable execution, an owner, an operator procedure, or current documentation.

The verification requests above address those missing facts. They are read-only requests, not authorization to implement, contact customers, publish content, take payments, or modify production.

Important distinctions:

- A tool registered to a voice agent is a backend capability and a partial user-facing entry point. It is not proof that callers can discover it, complete the task, recover from failure, or receive an accurate completion message.
- An HTTP route is not proof of a complete frontend or a production-ready workflow.
- A public API can intentionally lack a browser interface. A separate GUI is not automatically a gap when a usable voice or operator interface meets the promise.
- Authentik on sites.floridamanweb.online does not establish authorization on the other hosts.
- Twilio signature validation establishes webhook provenance when correctly enforced. It does not, by itself, establish business ownership or authorize account changes.
- Voice enrollment endpoints do not establish that enrolled voice verification is used, required, effective, or the right authorization mechanism.
- A merged PR is not the same as a healthy deployment. A healthy deployment is not the same as verified customer-visible success.
- Manual delivery is not automatically a broken product. Undisclosed, unowned, untracked, or unbounded manual delivery is a gap.
- A timeout reaching the Kubernetes API does not prove that public sites or the voice service are unavailable.
- The approximate MCP tool inventory is not a complete tool-by-tool audit. The next evidence pass must enumerate the actual registry and associate each tool with an authorization and behavior contract.

2. Coverage notation

Each inventory row has four fields:

  F = frontend or role-appropriate interaction surface
  B = backend capability or supporting mechanism
  P = defined execution process or guideline
  D = feature-specific operator documentation

Values:

  Y = explicitly present in the supplied brief; not independently retested
  P = partial coverage established; important portions remain unverified
  U = presence or completeness not established
  R = a reported missing/manual soft spot; verification still required
  — = not applicable to that particular feature

Documentation rule:

The named document families exist, but their detailed coverage and current accuracy are unverified. Therefore most feature-specific D values are U. This does not mean those documents are absent.

Inventory evidence sources are consolidated under EVIDENCE. Gap references point to the ranked backlog under PLAN.

10. Target architecture and delivery decisions

10.1 Separate identity namespaces.

Customer ID, caller identity, telephone number, business identity, public hash, slug, payment identity, and authenticated operator are different concepts. Establish their actual mappings; do not treat any one as an interchangeable authorization token.

10.2 Separate state machines.

Maintain explicit contracts for:

- Customer relationship and funnel state.
- Communication consent and suppression.
- Callback/call execution.
- Requirements draft, confirmation, and revision.
- Build and change-request execution.
- Payment state and service entitlement.
- Publication state.
- Account removal and privacy requests.

The existing implementation may represent these differently. The required design property is separation of meaning, not a forced database rewrite.

10.3 Use durable, reconcilable side effects.

Callbacks, messages, builds, payment activation, publication, deployment, and deletion need stable operation identities, retry rules, visible failure states, and reconciliation. Aim for idempotent effects and recoverable processing rather than unsupported “exactly once” claims.

10.4 Keep authorization outside model discretion.

The assistant may propose or request an operation. Backend policy decides identity, tenant, entitlement, consent, allowed paths, permitted destinations, and whether step-up or approval is required.

10.5 Treat completion as evidence, not narration.

A task is complete only after its named effect is verified:

- Callback accepted is not callback attempted.
- Message accepted is not message delivered.
- Payment page opened is not payment verified.
- Build queued is not demo published.
- PR merged is not rollout healthy.
- Tool returned success is not personal data removed everywhere.
- Origin unpublication is not guaranteed removal from third-party copies or search engines.

10.6 Preserve current strengths.

Retain the fail-closed asset-graph audit, CI guard, trusted-phone framework, lifecycle primitives, signature validation, and existing mode separation while verifying their boundaries. Do not replace working systems merely to achieve architectural uniformity.

10.7 Require a complete operational envelope.

Every enabled feature needs:

- A truthful user entry and outcome.
- A safe backend contract.
- An accountable execution process.
- A failure/recovery path.
- An operator procedure.
- A test and evidence record.

An intentional manual step is acceptable only when assigned, visible, bounded, auditable, and consistent with the advertised promise.

10.8 Distinguish core completion from product expansion.

A web directory, visual owner editor, multilingual service, advanced introductions, custom domains, and recurring billing are not automatically current promises. Their priority rises if actual public copy or customer agreements promise them.

7. Ordered end-state verification checklist — owner: grok

Use controlled fixtures and isolated environments first. Any live customer contact, payment, publication, destructive test, restore, or rollout needs separate explicit authorization and scope.

V01. Freeze the promise baseline.
  Collect exact landing, prompt, agreement, and client-page promises. Associate every CTA, fee, entitlement, turnaround claim, and privacy statement with a test. Unresolved promises cannot be omitted merely because they are hard to test.

V02. Verify the surface and deployment inventory.
  Independently verify the public landing, generated-site host, voice service, authenticated CRM, and MCP boundary. Reconcile the supplied 261-site snapshot against the authoritative active catalog; do not assume historical count equals current published inventory.

V03. Verify public asset and page closure.
  Check expected page status, content type, referenced assets, internal links, generation consistency, and deployed revision. Exercise browser runtime behavior where static checks are insufficient. Cache behavior must not reintroduce broken graphs.

V04. Verify identity mappings and mode routing.
  Use fixtures for public callers, prospects, paid owners, front desks, unknown/shared/reassigned numbers, ambiguous multi-business ownership, and do-not-call records. Confirm deterministic intended routing and no privilege gain through caller claims.

V05. Verify route and tool authorization.
  Exercise allowed and denied caller/operator/tenant combinations for every exposed mutation and private read. Include registration/customer listing, callback placement, mark-paid, owner enrollment, trusted phones, lifecycle operations, MCP, personal pages, audio, and hosted requests as applicable.

V06. Verify consent and communication suppression.
  Test consent capture, scope, revocation, opt-out, pending callback/message cancellation, and re-opt-in. Check current sender/traffic eligibility. Confirm all relevant sending and dialing paths consult the same effective policy.

V07. Verify ingress and cost containment.
  Test invalid signatures, retries, malformed payloads, request floods, oversized input, prohibited destinations, and dependency errors. Confirm bounded side effects, deduplication, spending controls, and useful operator signals.

V08. Verify a complete public call.
  From the supported public entry, test greeting, disclosures, lookup, clarification, a tool failure, interruption, silence, repeat request, outcome logging, and clean call termination. Confirm the assistant never claims a tool action succeeded when it did not.

V09. Verify directory and knowledge truthfulness.
  Compare known fixtures against authoritative business facts. Test duplicate names, changed hours/contact data, no results, out-of-area requests, stale sources, and malicious retrieved content. Confirm appropriate uncertainty and correction pathways.

V10. Verify events and activities.
  Test category summaries, detail lookup, source lists, recurring events, canceled/expired events, time zones, missing fields, and duplicates. Summaries and details must agree, with freshness policy enforced.

V11. Verify broadcasts and moderation.
  Exercise safe submission, required confirmation/moderation, listing, ownership-bound deletion, reporting, operator removal, and expiration. Test impersonation, doxxing, injection, and unauthorized deletion using controlled content.

V12. Verify QOTD.
  Check active question selection, answer submission, repeat-answer semantics, visibility, suggestions, moderation, rollover, and an empty/unavailable state.

V13. Verify profiles and event interests.
  Check preference correction, matching explanations, interest withdrawal, blocking, and contact-sharing policy. Confirm that another caller cannot retrieve private profile data or infer unauthorized contact details through match lists.

V14. Verify personal-page lifecycle.
  Check no publication before appropriate consent, correct public fields, accurate status, repeated requests, updates, opt-out, controlled-cache removal, and re-opt-in. Distinguish controlled unpublication from third-party copies the system cannot guarantee to erase.

V15. Verify registration through callback.
  Submit an authorized test registration and verify acknowledgment, durable queueing, scheduling, actual attempt reconciliation, no-answer handling, provider failure, duplicate submission, opt-out, and operator escalation.

V16. Verify onboarding through approved requirements.
  Interrupt and resume the interview, correct an earlier answer, attempt incomplete finalization, and produce an approved versioned brief. Confirm changes after finalization trigger the documented review/invalidation behavior.

V17. Verify build execution and recovery.
  Process a test brief through the actual human or automated operating model. Exercise worker interruption, duplicate claims, invalid content, failed tests, and recovery. Confirm bounded permissions and correct customer/job/artifact binding.

V18. Verify demo publication and delivery.
  Check the intended demo in a browser, its functional CTAs/forms, responsive/accessibility behavior, and asset graph. Send only to authorized test destinations; verify provider responses and failure handling without equating accepted delivery with human receipt.

V19. Verify sales and payment activation.
  Confirm accurate offer presentation and approved outreach. Test manual activation safeguards and, when implemented, signed duplicate/out-of-order provider events, delayed settlement, unmatched payments, refunds/disputes, and reconciliation. Entitlement must follow the documented financial contract.

V20. Verify owner enrollment, step-up, and recovery.
  Test a legitimate owner, impostor, expired proof, replay, lost phone, shared number, and last-trusted-phone removal. Where voice enrollment is used, test consent, enrollment failure, deletion, and the alternate recovery route.

V21. Verify owner update through healthy release.
  Request a supported edit, inspect the request, exercise rejection and cancellation, create the approved change, and follow its PR/image/deployment evidence. A merged-but-failed rollout must not become shipped or trigger a success notice.

V22. Verify rollback and publication consistency.
  Restore a known-good release in a safe test scope. Confirm site assets, content, request states, knowledge/index versions, and notifications remain consistent. Confirm unrelated tenants are unaffected.

V23. Verify front-desk and hosted request behavior.
  Resolve the correct business, answer only supported published facts, process a permitted inquiry, and test unavailable knowledge and unsupported transactions. Confirm inquiries reach an accountable recipient and are not misrepresented as accepted bookings/orders.

V24. Verify churn, removal, and lifecycle cancellation.
  Independently test stopping outreach, billing changes where applicable, entitlement changes, publication removal, pending-operation cancellation, and retention. Confirm each effect follows the requested scope and requires appropriate authority.

V25. Verify backup restoration and state reconciliation.
  Restore representative data into an isolated environment, measure recovery against approved objectives, and reconcile externally completed operations. Confirm privacy removals, suppression, and deletion tombstones are not lost.

V26. Verify dependency-outage behavior.
  Exercise unavailable telephony, messaging, model, memory/vector store, billing reconciliation, deployment control plane, and other relevant dependencies. Confirm safe degradation, durable work, truthful user responses, alerting, and nonduplicative recovery.
